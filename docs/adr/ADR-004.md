# ADR-004: cm Dev Wrapper vs Compiled Binary

**Status**: Accepted
**Date**: 2026-02-22
**Deciders**: NTM core team

## Context

The `cm` CLI (CASS Memory) ships in two forms:

1. **Dev wrapper** (`~/.local/bin/cm`) — a shell script that runs `exec bun run /path/to/src/cm.ts "$@"`. This is the standard installation for developers working on or with `cm` directly.
2. **Compiled binary** (`dist/cass-memory`) — a Bun standalone binary built for distribution. This binary has historically had runtime issues with `onnxruntime-web` failing to load in Bun's compiled bundle context, which affects semantic embedding features.

The NTM supervisor starts `cm` by resolving `cm` from the system PATH. It does not hardcode a path to either form.

## Decision

NTM's supervisor uses whichever `cm` binary is first on PATH. On developer machines, `~/.local/bin/cm` (the bun dev wrapper) takes precedence and is fully functional, including all embedding features. The compiled `dist/cass-memory` binary serves as the distribution artifact for CI and production environments where the full source tree and `bun` runtime are not available.

## Consequences

- On developer machines, the supervisor always uses the dev wrapper. Changes to `src/cm.ts` take effect immediately without a rebuild, which accelerates iteration.
- In production or CI environments, `cm` must either be the compiled binary or an explicitly installed version. If the compiled binary is used and `onnxruntime-web` fails to load, semantic search falls back to keyword-only mode (degraded but functional).
- There is no pinned version enforcement at the supervisor level. Version drift between the dev wrapper and the compiled binary is possible and must be managed by the operator.
