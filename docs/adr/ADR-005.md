# ADR-005: Git Remote Split — Fetch Upstream, Push Fork

**Status**: Accepted
**Date**: 2026-02-22
**Deciders**: NTM core team

## Context

The canonical NTM repository is `Dicklesworthstone/ntm`. Contributors without direct push access to the canonical repo work on a personal fork (`jonathan-kellerai/ntm`). Without an explicit split remote configuration, a developer must either maintain two named remotes or risk accidentally pushing to the wrong destination.

## Decision

The `origin` remote is configured with split fetch/push URLs:

- **Fetch**: `https://github.com/Dicklesworthstone/ntm.git` (canonical upstream)
- **Push**: `https://github.com/jonathan-kellerai/ntm.git` (personal fork)

This means `git pull` (or `git fetch origin`) tracks upstream changes from the canonical repo, while `git push` sends changes to the personal fork without any additional flags or remote name disambiguation.

## Consequences

- Pull requests must be opened from `jonathan-kellerai/ntm` targeting `Dicklesworthstone/ntm`. This is the standard fork-and-PR workflow and GitHub surfaces it correctly.
- Running `git push` without additional arguments always pushes to the fork, which is the correct behavior for contributors. There is no risk of accidentally pushing to the canonical repo.
- Force pushes to the fork's `main` branch are safe because it is a personal fork, but care should still be taken to avoid rebasing commits already referenced in open PRs.
- Any developer cloning the canonical repo directly (without the split remote setup) will push to the canonical repo if they have write access, bypassing the fork PR workflow. The split remote setup must be applied manually after cloning.
